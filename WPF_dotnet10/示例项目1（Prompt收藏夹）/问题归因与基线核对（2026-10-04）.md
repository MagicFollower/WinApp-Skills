**本文定位**：一次纯核对与归因，不改 `app/` 的实现。记录三件事——`lib/` 以谁为基准、对齐做了什么、以及上一轮列出的那堆"可优化点"**背后的共同机制**。文末归档本轮的"问题 + 答案"，供下一轮（打磨工具本身）接手。

## 一、基线核对：谁是基准，以及为什么"版本号"这次不顶用

包内有两份 StartUI4Controls 源码：

| 位置 | 角色 | 关键时间（mtime） |
|---|---|---|
| `../组件源码与组件使用说明/StartUI4Controls/` | **本轮认定的基准** | `UI4ThemePacks.cs` 10-02 16:52、`README.md` 10-02 23:01 |
| `lib/`（示例工程内） | 被对齐方 | `UI4ThemePacks.cs` 10-02 16:17、`README.md` 10-02 16:23 |

**判方向的过程本身值得记**，因为它暴露了一个机制缺口：

1. 两份 `StartUI4Controls.csproj` 都是 `<Version>3.0.0</Version>`、`<FileVersion>3.0.0</FileVersion>`、`<AssemblyVersion>3.0.0</AssemblyVersion>`。**版本号不能区分它们**，所以"谁新"没有库内证据。
2. mtime 只能给方向、不能给身份（拷贝、解压、编辑都会改它）。
3. 真正立得住的是第三方参照：把基准目录与 Skill `startui4-wpf` 的 `assets/seed/lib` 逐文件比对（忽略行尾 CR）→ **零差异**；而 `lib/` 与该参照之间差 2 个文件内容、缺 1 个文件。所以基准 = 外部那份，是靠"与独立参照一致"推出来的。

**结论**：对齐前的差异不是"工程里打了本地补丁"，而是**单纯落后**。`lib/` 的 44 个 `.cs` 里除 `UI4ThemePacks.cs` 外与基准逐文件相同，没有任何一处是宿主自己改的——这点很重要，意味着这次同步零冲突、也不需要保留任何工程侧改法。

差异全集（三个动作，别的都没差）：

| 文件 | 差异性质 |
|---|---|
| `UI4ThemePacks.cs` | 仅 `PaperWhite` / `PaperGrey` 两段调色值 + 对应注释（旧：墨褐/暖灰手调；新：按 100-themes 的 polaroid/day、tundra/day）。**公开成员签名完全一致，无 API 变化**（逐行比对 `public static` / `public const` 集合，差集为空） |
| `README.md` | 身份错配：`lib/README.md` 实际是 **619 行的《组件库架构审计报告》**（2.0.0 时点，含已删除的 `IThemeAware` / `TrackControl` 讨论），基准那份是 **2128 行的《组件手册》**（属性/事件/枚举的权威参考） |
| 《架构审计报告-3.0.0主题机制评审.md》 | 基准里有，`lib/` 里缺 |

## 三、根因归纳：五条链，以及它们怎么互相放大

上一轮我按"配色 / 文档 / 数据 / 交互 / 分层"分了五组症状。**分组是按文件位置分的，不是按成因分的**，所以照单逐条修完，同样的漂移下一轮还会再来。下面按成因重新收敛。

### 根因 1：配色有"三条并行通路"，而库对写错的键**不给任何反馈**

- **症状面**：同一份终端靛色值在代码里有三条取用通路——① `{x:Static h:Theme.Accent}`（编译期常量，7 处，永不跟主题）；② `{DynamicResource App.Brush.*}`（`App.xaml:16-20` 的 5 把刷子，色值是 `Helpers/Theme.cs:21-27` 的**第二份手抄**，`#4F6BE8` 就是 `Theme.Accent`）；③ `{DynamicResource UI4.Brush.*}`（令牌，唯一的主题通路）。`MainWindow.xaml:34-36` 一个按钮上三条同时用。另有 code-behind 直接 `Foreground = Brushes.White/Black` + `GradientStart = Theme.Accent`（`EntryListView.xaml.cs:82-127`、`ModuleListView.xaml.cs:169-185`）。
- **机制**：这套库是零 XAML、模板全 C# 构建，资源键由令牌枚举名**逐字**决定（`UI4.Color.<名>` / `UI4.Brush.<名>`）。**键名写错不报编译错、不抛异常**，只表现为"这一处没跟主题"。本地赋值即退订主题也是设计（`SetResourceReference` 占的就是本地值槽）。所以三条并存不会崩，只会**静默分叉**——改色时改一条，另两条不动，谁也发现不了。
- **为什么闸门抓不到**：`SettingsSelfTest` 的 29 组断言全在设置编解码的纯函数域，**对色源与资源键零覆盖**。绿灯与界面漂移可以长期共存。
- **一次性修到机制层**：① 先定"浅色单档定死"还是"要开暗色/套装"——这条决定 ①②③ 里该保留哪条；② 无论选哪条，都让 `App.Brush.*` 由 `Theme.cs` **派生**而不是重抄（一个 `RegisterAppTheme()` 顺带 `Resources["App.Brush.Accent"] = new SolidColorBrush(Theme.Accent)` 就够了）；③ 给 selftest 加一组"38 个令牌的 `UI4.Color.*`/`UI4.Brush.*` + 两个别名键在字典里齐全、且底色与 `Dark()` 定义同源"的断言——这是唯一能机器化抓"键名写错"的判据。**代价**：中等，改动集中在 `App.xaml.cs` + 新增断言文件，但要求一次把 27 个覆盖点重新过一遍亮度对比。
- **本轮已显式更正的口径**：库现有 **38** 个令牌（不是旧文档说的 30），`RegisterAppTheme()` 显式覆盖 **27** 个，其余 **11 个静默继承库内置 `Light()`**：`OnAccent`、`Shadow`、`ScrollBarThumb`、`Separator`、`BorderWeak`、`TextMuted`、`BackgroundGradientStart`、`BackgroundGradientEnd`、`HoverOverlay`、`SelectedOverlay`、`TrackBackground`。其中 8 个正是库 10-02"第二轮补齐"新增的。**这次扩容对宿主是隐形变更**：没报错、没测试失败、浅色下库默认值本来就够浅，所以旧文档里的"30"是当时真实生效的规模，不是有人写错数字。

### 根因 2：库靠整份源码拷贝自包含，但拷贝**没有指纹**

- **症状面**：两个 `3.0.0` 挂着不同源码共存（§一）；`lib/README.md` 顶着"手册"的文件名装着一份历史评审；设计方案 §21 里引用了 net10 版不存在的 `UI4DataGrid.cs`。
- **机制**：`lib/` 用源码工程引用（`<ProjectReference Include="../lib/StartUI4Controls.csproj" />`）是刻意的自包含设计——好处是模板改动能就地重编、交付包能独立重建；代价是**每次同步都是人肉 diff**，而且没有任何"这份拷贝来自哪个 commit / 哪些文件被宿主改过"的记载。同版本号可共存就是这么来的。
- **一次性修到机制层**：把 §一的比对过程固化——`lib/` 里放一份 `SOURCE-BASELINE.json`（基准目录 + 逐文件 sha1 + 对齐日期），同步用一条脚本判"是否落后 / 是否有宿主本地改动"。**代价**：小（一次性建清单，之后每次 cp 顺带重算）。这条不做，下一轮库改版时同样的分叉一定会再出现。

### 根因 3：有一挡"绿灯"其实什么也不证明

- **症状面**：`publish*.cmd` 第 2 步就是 `--selftest`，退出码非 0 才告警；而它测的全是纯函数。
- **机制**：`SettingsSelfTest` 的价值是真实的——它钉住了 §22 那次 16 MB 事故的机制（"连续 5 轮序列化文本长度不增"直接对指数膨胀设防）。但它**不碰** `FrontmatterParser` 的任何往返、不碰仓储与 `PromptService` 的任何 IO、不碰主题资源键、不碰 UI 绑定。于是"门禁通过"的语义被压缩成"设置编解码没退化"，数据层真正的风险没有任何一挡能抓——只剩设计方案 §20 那 20 条**全空的验收 checkbox**（人肉判据等于没判据）。
- **典型放大案例（两条症状其实是同一件事）**：`PromptModule` 是纯 POCO 没有 INPC（`Models/PromptModule.cs`），`RefreshModuleCounts` 却就地改 `existing.EntryCount`（`ModuleListViewModel.cs:171-180`），而 XAML 绑的是 `{Binding EntryCount}`（`ModuleListView.xaml:77`）→ 计数变化**永不通知 UI**。它之所以看起来正常，是因为另一条路径 `RefreshModules()` 用 `Modules.Clear()` + 逐条 `Add` 整表重建（`:137-139`），重建时新读到的值被顺带刷出来了。也就是说：**"整表重建"这个性能面上的坏做法，恰好掩盖了"缺 INPC"这个正确性面上的缺陷**。下一轮如果只优化性能（改成增量 diff）而不补 INPC，这个潜伏的 bug 会当场显形——所以这两件事必须同批做，这是归因直接改变修复顺序的一个例子。
- **一次性修到机制层**：把 selftest 从"设置专项"升成"数据契约专项"：`FrontmatterParser` 往返（含未知键保留）、`FileSystemRepository` 在临时目录里的读写/改名/移动、`SaveEntry` 中途失败后的可恢复性。**代价**：中等，需要测试用临时目录与清理逻辑；收益是后面每次动数据层都有一挡真能挡。

### 根因 4：库能力与宿主手写实现并存，"哪些地方退了订"没有清单

- **症状面**：应用只用 7 个 UI4 控件（`Button`/`ListBox`/`TextBox`/`ComboBox`/`CodeEditor`/`ContextMenu`/`MessageBox`），卡片、Toast、选中态、排序胶囊都是 `Border` + `DropShadowEffect` + 本地赋值手搓；`UI4Panel` / `UI4ListView` / `UI4GridView` 一个没用。`App.xaml` 里 `InverseBool`、`SortModeMatch` 两个转换器注册后全文零引用，`App.Brush.Accent`/`Neutral`/`NeutralHover` 也是注册了没被 XAML 用（同色值改走 `{x:Static}`）。
- **机制**：本地赋值退订是库的设计，不是缺陷；**缺的是"退订点清单"**。今天 light-only 单档下这些手搓与退订全部自洽，一旦开暗色就是"逐处回忆哪些地方写死了色"，而回忆是最不可靠的机制。另外，库的悬浮放大/阴影外溢这类契约（`ItemMargin ≥ 10`、外边距 ≥ `ShadowDepth + ShadowBlurRadius`）本轮没被触发，**只是因为没用那几个控件**，不构成"项目符合契约"的证据——唯一一处手写阴影 `MainWindow.xaml:86`（`BlurRadius=12 ShadowDepth=2`，需 14 px 净空）对上边距 16 px，是压线过的。间距刻度上另有 8 处非 4 倍数值（`2`/`6`/`10`），属观感一致性问题，不是缺陷。
- **一次性修到机制层**：要么显式声明"本项目定死死浅色，不退订需理由"并把 `x:Static` 那 7 处收进 `App.Brush.*`；要么走完整主题化（卡片换 `UI4Panel`、列表换 `UI4ListView`，同时按契约给足 margin）。**这是产品决策，不该由修 bug 顺手决定**——需要你先答"要不要暗色/套装"。

### 根因 5：文档承载的是"过程记忆"，读者把它当"当前契约"

- **症状面**：本轮纠正的 6 处（30→38 令牌、23→29 断言、5→7 控件、`tools/make-icon.ps1`、`tools/verify-icon.ps1`、首行截图）+ 设计方案里那份未随包交付的《剪贴板卡顿问题报告.md》引用。
- **机制**：这些数字**写的时候都是对的**，它们是"那一次工作的记录"。真正的问题是：交付包在某个时刻被裁剪过（`tools/` 整个没了、截图与报告没进来），而**裁剪没有留下"哪些引用因此失效"的账**；同时仓库里既没有机器闸门反驳过期数字（根因 3），也没有区分"历史叙事"与"当前契约"的段落约定。所以最容易被误读的是《教程》第五节那张实测表——里面的结论都成立，但产出它们的脚本已经不在了，读的人以为还能重跑。
- **处置**：本轮已按"矛盾处显式更正、不抹掉历史值"改写（例：`PASS 断言组=23` 保留为历史实测值并注明 10-04 复测 29）。**建议后续把 README 拆成"当前契约"与"迁移/事故记录"两节**，后者加时点标注。

## 五、下一轮（打磨工具本身）的建议顺序

顺序**按根因排，不按分组排**——根因 3 的结论直接决定了：先给判据，再动实现，否则改完照样只能靠肉体验收。

| 优先 | 事项 | 为什么先它 | 判据 |
|---|---|---|---|
| P0 | selftest 扩面：`FrontmatterParser` 往返 + 仓储在临时目录的读写/改名/移动 + 主题键完整性 | 不加判据的修复无法验证（根因 3、1） | 新增断言能在"故意破坏"时变红，正常时退 0 |

### 8.2 区分性实验（这一批的四条）

1. **`File.Replace` 在目标不存在时到底行不行**——分叉版 `WriteEntry` 用的是无条件 `File.Replace(tmp, path, null)`。为判清"这是不是缺陷"而不是猜，写了一个最小 C# 控制台程序实测：目标不存在时 `File.Replace` 抛 `FileNotFoundException` 且 `.tmp` 残留在磁盘上，`File.Move` 同条件下成功。主线按 `File.Exists` 分两条路（存在走 `Replace`、不存在走 `Move`），所以新建条目不会被这条打死。附带纠正一次我自己的误判：先用 PowerShell `[IO.File]::Replace($src,$dst,$null)` 探，报"路径的形式不合法"——那是 PS 把 `$null` 转成空串造成的**自伤证据**，不作数，结论以 C# 探针为准。

## 九、第四批：截图反馈的两处观感问题归因

用户给了一张截图（`PixPin_2026-10-04_16-08-56.png`），指出两件事。两件的归因层级完全不同，分开记。

### 9.1 「+」按钮内容偏移 —— 归因在"宿主钉死尺寸 × 库默认内边距"的乘积上

第一眼会以为是**没居中**。实际读源码：`lib/UI4Button.cs:160-161` 的 `ContentPresenter` 两向都是 `Center`，居中是有的。真因是这两条相乘：

- 宿主给圆钮写了 `Width="28" Height="28"`；
- 库的样式默认 `Padding = 10,0,10,0`（`lib/UI4Button.cs:135`）。

于是内容区只剩 **28 − 20 = 8 px 宽**。字号 16（默认档的图标层级）时「+」的字身就已经 > 8 px：居中的 presenter 被 arrange 成 8 px，文字从它自己的左上角起画，整体就朝**右下**偏，还会被切掉一点。所以"加 `HorizontalContentAlignment`"这条最常见的处置是无效的——它已经居中了。

处置落在宿主层（钉死尺寸的是宿主，不是库）：`Padding="0"`，尺寸与半径改为读 `Typography` 按基准派生的资源键（`App.Size.RoundButton` / `App.Radius.RoundButton` / `App.Size.Chip` / `App.Radius.Chip`）。基准 15 时算出来仍是 28 与 24，**默认观感逐像素不变**，放大档才长。半径发布成 `CornerRadius` 对象而不是 `double`：`DynamicResource` 不做类型转换，往 `CornerRadius` 依赖属性上挂 double 会在运行期炸。

同一族站点一并处理（不修就是下一档字号再报一次）：两栏 8 个排序胶囊、收藏胶囊、详情区 `[收起]`、设置面板两个「恢复默认」按钮。

判据与负向自证：`DisplaySelfTest` 钉住"默认基准下圆钮 28 / 胶囊 24"与"12–28 全区间 ≥ 字身 × 1.3"；把 `RoundButtonSize` 改回恒返回 28 → 退出码 `8`，从基准 21 起逐档 `FAIL [display] 基准 21 时圆钮 28 px 装不下 22 px 的图标字身`；回滚后 `diff` 无输出、`--selftest` 回到 236 组全绿。

### 9.2 两栏宽度与头部内缩 —— 归因是"两个数字各自为政"，不是布局算错

- 左栏头部 `Padding="12,10,12,6"`、中栏 `Padding="8,8,8,4"`：两栏的左起笔与右收笔本来就不一样，「+」到列边的距离自然一个 12 一个 8。
- 中栏的「★ 收藏」是 `DockPanel` 的末子，`LastChildFill` 默认 `true` → 被拉成通栏条。它不是"宽度算错了"，是**这条根本没有内容宽这个概念**。
- 列宽 200 / 280 是历史值：内缩统一到 12 之后，200 栏里三个排序胶囊只剩 4 px 余量，280 栏里五个胶囊在字号 18 就换行。

处置（数字由用户选定，见 README 文末第四批表）：两栏头部内缩统一 `Padding="12,8"`；两个 `DockPanel` 显式 `LastChildFill="False"`；列宽 220 / 300。

这一条**没有可机器化的判据**（"齐不齐""顺不顺眼"是观感），所以留作目测项：220/300 下两栏「+」是否齐、收藏胶囊收成内容宽是否可接受、字号 20 与 28 两档下「+」与胶囊的字是否还在正中。

## 十、第五批：同一屏的三条反馈归因（同日）

### 10.1 「+」没居中 —— 第二层原因：字符本身的墨迹不在 em 框中心

第四批把"槽位被库默认 `Padding` 吃掉"修掉之后，逐像素读用户新截图（`PixPin_2026-10-04_16-19-32.png`）：圆钮 bbox 28×30、墨迹 8×8，**水平 dx=−0.5 px 已经居中**，但**垂直 dy=+1.5~2 px**。也就是说槽位那条只解释了一半，剩下的是字体度量：`+` 在 Segoe UI 里的墨迹中心低于 em 框中心，行盒里还留着 descent 空间，字号越大这个差越明显。

这类问题有两条路：给 `TextBlock` 加负 `Margin`（差值随字号变，等于把魔法数字写死一遍），或换一个**按光学居中设计**的字形。选了后者：`Segoe MDL2 Assets` 的 `Add`（`\uE710`），与工具栏那个文件夹按钮同一支字体。图标字体不吃用户选的字体族（本地赋 `FontFamily` = 退订，这是库的设计，也是这里要的语义）。

复核方式改成了自证：起我自己那个实例 → `GetWindowRect` + `CopyFromScreen` 抓客户区 → 逐像素找圆心与字心。125% DPI 下两枚圆钮：

| 位置 | 圆心 | 竖笔 | 横笔 | 偏差 |
|---|---|---|---|---|
| 左栏 | (200.5, 106) | x=200..202 | y=105..106 | ±0.5 设备像素 |
| 中栏 | (504, 106) | x=504..505 | y=105..106 | ±0.5 设备像素 |

顺带记一条方法论：第一版测量脚本把"圆内白像素"直接取 bbox，结果 bbox 等于整枚圆——因为方形 bbox 的四个角在圆外、那里是白的页面底色。**在圆内取色必须限制在内切圆里**，否则测出来的一定是"完美居中"，是个假阳性陷阱。

### 10.2 收藏胶囊与胶囊块不等宽 —— DockPanel 给不出"与下一行同宽"

上一批我把它从 `LastChildFill` 的通栏改成按内容收宽，方向反了；但即便让它 stretch，`DockPanel` 的末子也只能填到「+」的左边，比下面那排胶囊短一个按钮宽。"与所有按钮的宽度之和对齐"这句话在 `DockPanel` 里没有对应物——它需要的是**两行共享同一个列宽**。

处置：头部换成 `Grid`（`*` + `Auto`），收藏胶囊与 `WrapPanel` 都在第 0 列、`+` 在第 1 列。宽度相等由结构保证，不需要算像素，也不随字号漂移。

### 10.3 恢复默认后下拉框不跟着变 —— ComboBox 会静默清空"列表外的选中值"

`Fonts.SystemFontFamilies` 里没有"出厂字体栈"那个复合串（`Segoe UI, Microsoft YaHei UI, sans-serif`），而 `ResetTypography()` 把 `SelectedItem` 设成了它。WPF 的 `Selector` 在挂了 `ItemsSource` 时，对不在源里的值会**清空选择**而不是报错——所以生效字体确实回到了出厂栈（界面字变了），只有下拉框的标签没跟着变，看着像"恢复默认没起作用"。

处置把这条变成结构性的：候选表由纯函数 `Typography.BuildFamilyChoices(systemSources)` 生成，**出厂项固定第 0 位**，其余去重、丢空白、按序；`SelectedFontFamily` 的类型从 `FontFamily` 换成 `string`（相等判定精确，不依赖 `FontFamily.Equals` 对方括号复合族的口径）；选中出厂项时设置里存空串，让"没设置过"与"设成出厂值"是同一个事实。启动时若存的字体名已不在表里（系统卸载、手改设置），回落到出厂项而不是留空白。

判据：`DisplaySelfTest.CheckFamilyChoices`，含"真实系统字体表首位必须是出厂项"（本机实测 93 项）。

## 十一、收藏胶囊与排序行等宽：两次不成立的方案与最后成立的那个

需求是"两行宽度对齐，且列被拖宽时收藏胶囊跟着变宽"。三条路都试了，前两条有反例：

| 方案 | 为什么不行（实测） |
|---|---|
| 收藏胶囊 `Stretch` 到列宽（`Grid` 两列 `*` + `Auto`） | 两行只在"排序胶囊刚好填满一行"时对齐。默认 300 列下胶囊块最宽一行到 462，胶囊被拉到 547 → 胶囊**比排序行长 85 px**，就是用户 16:38 截图圈出来的样子 |
| 第 0 列设 `Auto`，让列宽由"两者中较宽的"决定 | `WrapPanel` 在 `Auto` 列里拿到的可用宽度近乎无限，于是**不换行**：5 个胶囊排成一行、列被撑到 306 px（超过 300 的列宽），「+」被挤出可视区。抓屏里那一行只有 4 个灰胶囊 + 1 个高亮胶囊顶到 545、而「+」不见了，就是这个反例 |
| 收藏胶囊 `MinWidth="{Binding ActualWidth, ElementName=SortChips}"` | 跨两行的布局回写有一拍滞后：胶囊块最终 197 px，收藏胶囊停在 172 px（那是字体生效前一次的宽度），没有第二次布局把它推平 → 实测差 24 px |
| **`StackPanel` 夹心**（`Grid(* + Auto)` 的第 0 列放一个 `HorizontalAlignment=Left` 的 StackPanel，里面依次是收藏胶囊 `Stretch` 与 `WrapPanel`） | 成立。StackPanel 的期望宽 = 子项中最宽者 = 排序胶囊最宽一行；它按 Left 对齐所以 arrange 宽 = 期望宽；收藏胶囊 `Stretch` 到这个宽 → 两行严格等宽。列变宽 → `WrapPanel` 可用宽度变大 → 换行减少 → 最宽一行变宽 → 胶囊同步变宽。实测 300 列 264..496 vs 495、420 列 267..545 vs 544，两处都在 1 px 内 |

顺带一条：竖向 `StackPanel` 传给子项的是**有限的宽度约束**（只有堆叠方向是无限的），所以它里面的 `WrapPanel` 会正常换行——这正是 `Auto` 列做不到的那一点。
