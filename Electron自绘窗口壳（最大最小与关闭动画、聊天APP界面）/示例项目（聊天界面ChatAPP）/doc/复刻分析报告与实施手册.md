# 第一章 产品概述与设计架构

## 1.1 产品定位

一款 Windows 桌面即时通讯(IM)应用,视觉风格接近 Telegram Desktop 的现代化变体:**悬浮圆角窗口 + 毛玻璃/渐变质感 + 三栏式信息架构**。原型图展示了同一应用的两种状态(上:默认表情面板;下:定制表情 + 群成员/快捷短语),核心界面由三个窗口级区域构成。

## 1.2 信息架构(IA)

```
应用
├── 会话列表栏(左,固定宽)
│   ├── 侧边导航按钮(≡)
│   ├── 全局搜索(搜索联系人…)
│   ├── 会话过滤器(全部 / 个人 / 群聊 / 空间)
│   └── 会话列表(头像 + 名称 + 成员数)
├── 聊天主区(中,弹性宽)
│   ├── 聊天头部(悬浮胶囊:群信息 + 通知/菜单)
│   ├── 消息流(文字/图片/大表情/引用/系统消息)
│   └── 输入工具栏(悬浮胶囊:附件/图片/输入框/表情/发送)
└── 右侧面板(可开关,固定宽)
    ├── 表情面板(全部 / 定制 / 动态 / 贴纸 / 手势)
    ├── 群成员(可展开)
    └── 快捷短语(可折叠,666,+ 添加)
```

## 1.3 窗口体系

原型图呈现「桌面壁纸上悬浮一个主窗口」的形态,窗口本身:

- **无边框**(自绘标题栏区域,原型中未见原生标题栏);
- **大圆角**(整体窗口四角统一圆角);
- **透明/半透明背景**,透出后方橙粉色渐变桌面;
- **窗口移动与控制全部自绘**(2026-10-11 本轮12起):不用 `-webkit-app-region`(它会把右键交给 OS),拖拽由 `pointerdown` + IPC 交给主进程搬窗,窗口控制(最小/最大/关闭)在拖拽带上右键浮出,最小化退场动画自绘(见 6.4、4.8.1、T0Level §19);
- 窗口内再分三层:最底是**全局光影流动背景**,中间聊天区**无卡片**、直接落在该背景上并上下出血,左右两栏是**悬浮圆角卡片**压在中间层之上,卡片与中间区之间留间隔;
- 三个栏位之间**无硬分割线**,靠背景色块与留白区分。

## 2.8 响应式约束(2026-10-11 本轮11 重定:等比收缩取代浮层挡)

用户口径的三条硬要求:**窄窗时两侧卡片不许与中间区重叠**、**左右两侧宽度恒等**、**中间区最小宽 = 侧栏宽度的 2 倍**。落法与理由:

- **侧栏宽由一条 clamp 算出,不交给 flex**:`.window` 上写
  `--side-w: clamp(var(--col-side-min), (100cqw - 2 * var(--gap-side)) / 4, var(--col-side));`,
  两侧都 `flex: 0 0 var(--side-w)`,中间区 `flex: 1 1 0; min-width: 0` 吃剩下的。
  未夹住时中间区恰好 = 2× 侧栏;夹在上限 300(窗口 ≥1248)时 > 2×。
- **为什么不能靠 flex 收缩来保证等宽**:flex 的收缩量是按**内容盒**基线分配的,而 `box-sizing: border-box` 下要先减掉 padding。右栏有 12+12 的横向内边距,于是它每一挡都比左栏少缩一点——实测早先差 24px、改一轮后仍差 **5.9px**。写死宽度让两侧同源,差值恒为 **0**。附带一条:`flex-basis: 0` 在 border-box 下会被 padding 减到 0 后夹住,padding 反而漏进边框盒,所以"等宽"和"铺满"是两件事。
- **`100cqw` 而不是视口媒体查询**:`.window { container-type: inline-size }`,容器查询长度量的是它自己的 **content box**(= 窗口宽 − 2×`--gap-window`)。浏览器预览下窗口宽 ≠ 视口宽(实测 1271 视口 → 窗口 1180),用 `@media` 会在错误的宽度上翻转。`100cqw` 写在 `.window` 自己的自定义属性里也解析正确。
- **`minWidth: 1248` 把不可达的挡位钉死**:1248 = 内容盒 1228 = `2×300 + 600 + 2×14`,正是"中间区 = 2× 侧栏"那一格的算术解。所以**真窗口里侧栏恒为 300**,等比收缩那条支路只在浏览器预览(`html.browser .window { max-width: 96vw }`)或有人调小 `minWidth` 时才走到。低于 `4×220 + 2×14 + 2×10 = 928` 三栏会溢出被裁,这就是 `--col-side-min` 的作用域。
- **原 `< 1120 右栏转浮层` 整条撤销**:`@container (max-width: 1100px)` 那一整块规则已删,`--panel-footprint` / `--head-reserve` 随之删除(见 2.2)。原因:浮层是"避让"而不是"共存",它本身就是重叠观感的来源之一,而等比收缩 + 下限让它没必要存在。
- **顺手抓到一条静默失效**:`overflow-y: auto` 会把同轴的 `overflow-x: visible` 升格成 `auto`,于是表情网格在窄挡出现**幽灵横向滚动条**。改 `.emoji-grid { overflow-x: clip }` + 网格列写 `repeat(6|9, minmax(0,1fr))`(`1fr` = `minmax(auto,1fr)`,不写 `minmax(0,…)` 时轨道不会缩到 min-content 以下)。判据要读 `.emoji-grid` **自己**的 `scrollWidth − clientWidth`,读父级得到 0(实测)。

### 4.1.1 G2(曲率连续)圆角(已落地 2026-10-11)

**动机**:`border-radius` 在直线与圆弧的接缝处曲率从 0 跳到 1/r,只有 G1;32px 这种量级能看出"突然圆起来"的折角感。G2 要接缝处曲率为 0 再平滑上升 → 超椭圆 `|a/r|^p + |b/r|^p = 1`(p=2 就是圆弧,p=4 即 squircle 家族)。

**实现(最终形态)= 一条 CSS 声明**:`corner-shape: superellipse(v)`,指数 **p = 2^v**(v=2 → p=4 = squircle;`round` 即 v=1 → p=2 = 圆弧)。它必须与非零 `border-radius` 同时存在,取值集中在 `--g2-shape`,作用元素是 app.css 文末那条规则列出的 **14 个圆角矩形**(2026-10-11 过滤行换成 GooeyNav 后,`.filter-tab` 从清单里摘除,新导航的胶囊与外框都是 `999px` 药丸,按上面的口径本就不参与;同日中间列做成第三张卡补进 `.chat-area`,右键浮出的窗口控制条补进 `.win-menu` 与 `.win-menu-btn`)。

- 引擎门槛:Chromium 139+;本工程 Electron 44.7 = **Chromium 152**(实测 `ready-to-show chromium=152.0.7977.130`)。不支持的内核整条忽略声明,画面自动退回圆弧——**不需要 JS,也不需要 `@supports` 分支**。
- 为什么一条就够:`corner-shape` 会带着 `background` / `border` / `outline` / **`box-shadow`** / **`backdrop-filter`** / **`overflow` 裁切**一起变形。阴影、磨砂、后代裁剪都跟着走,所以零结构改动。
- 命中区:与 `border-radius` 同类(纯绘制几何),不收缩点击热区。
- 覆盖范围:所有圆角矩形。`--r-pill` 与 `50%` 排除——它们没有"直线→圆弧"的接缝可谈曲率连续(实测这 9 个元素的 `cornerShape` 仍为 `round`)。

**两条被否决的实现(留档,含实测数字)**

1. **`clip-path: shape()`** —— Chromium 150 不支持:`from/close/z/百分比/calc/curve-to/arc-to/smooth-to/相对 by/填充规则/无逗号` 12 种写法读回 computed 全是 `none`,而同页 `circle()`/`inset()`/`path()` 都能读回。另:含 `var()` 的声明 `CSS.supports` 一律返回 true,判支持只能看 computed 读回。
2. **JS 逐元素生成 `clip-path: path()`** —— 能出形(按**角度**等分采样精确超椭圆,SEG=12 时最大几何误差 `7.16e-3r`;像素拟合对超椭圆偏差 0.4~2.1px、对圆弧 10.6~12.4px),但代价不划算:
   - `clip-path` 会把元素**自己的 `box-shadow`** 一起裁掉(同元素改 `filter: drop-shadow` 也不行,规范顺序先 filter 后 clip)→ 带阴影的 5 个表面(左右卡片、气泡、引用卡、chip)各要加一层 `::before` 重画;
   - 那层伪元素**不能** `background: inherit`:负 z-index 子层画在宿主背景**之上**,`--bubble-in` 0.92 / `--panel-bg` 0.72 这类半透明表面会叠两层变实(等于悄悄调成不透明);
   - 宿主的 `overflow:hidden` 必须放开(它连伪元素一起按 G1 裁,外鼓的角被削回圆弧),`.window` 的填充+磨砂还得下沉到 `.bg-layer`;
   - 共享开关规则 `html[data-g2-ready] [data-g2='fill']`(特异度 0,2,1)会盖过 `@container` 里 `.right-panel { position: absolute }`(0,1,0)——**窄窗浮层整个失效**,而且只在功能开启态下量布局完全看不出来,是 on/off 对照抓到的;**教训仍然有效**(共享开关规则会压过容器查询规则),但那条浮层分支本身已于本轮11 删除,见 2.8;(浮层分支本身已在 2.8 撤除,这条留作"共享开关规则的特异度会越过容器查询规则"这一族缺陷的实例)
   - 自定义属性会继承:磨砂做成 `--g2-blur` 挂在宿主上,右栏每个 `.chip` 的伪元素都多吃一层 blur → 双重模糊;
   - 运行时 95 个标记元素、内联 path 串 60,464 字节、JS +2.65 kB;改动面 = 4 个组件 + 1 个新 lib + 约 40 行 CSS。
   
   两条路都验过像素等价后换回原生 `corner-shape`。**结论:先查 `corner-shape`,别从 `clip-path` 起手。**

**几何真值**(`node .cache/g2-derive.mjs`,p=4):角部沿对角朝盒角外扩 `0.18921r` → r=32 为 6.05px,16 为 3.03,14 为 2.65,12 为 2.27,10 为 1.89,8 为 1.51,6 为 1.14。(同文件的 SEG 采样与命中区两节属于被否决的 JS 路径,留作对照。)

| 撤 blur 后(已落地) | 254,254,254 | −1.8 | **0** | 255,255,255 | −6.7 | **0** |

复采与首采逐位相同 → 不是采样抖动。

**归因**:`backdrop-filter` 把"被模糊的背景"按**元素自己的矩形 border-box** 合成,祖先 `.chat-area` 的 `overflow:hidden` + `border-radius` 裁得住普通内容、裁不住这一层;`.chat-fade` 是 `left:0;right:0` 的满宽矩形带,所以它的左下/左上角就露在弧外。三条独立差分(关 blur / 隐 fade / 给 fade 挂圆角)都能把饱和差从 27 拉回 0,而 `clip-path` 拉不回 —— 即 **`clip-path` 同样拦不住 backdrop-filter**。卡片自己的弧没问题:轮廓对 G2 偏差 2.1~3.1px(见 4.1.1 与 T0Level 16 节)。

**落地口径**(用户选):撤掉 `.chat-fade` 的 `backdrop-filter`,只留 `mask-image` 渐隐 + `--chat-veil` 洗色。代价如实记:卡内带区的观感有轻微变化(inside 采样 211.1→214.5、222.8→225.3),第 4 轮"渐变 + 模糊双层"退成单层。
**未采用的替代修法**:想保留模糊,就给 fade 自己挂 `border-radius:inherit;corner-shape:inherit`(实测同样把饱和差拉到 0,卡内观感与现状逐位相同);只挂 `border-radius` 不挂 `corner-shape` 时 fade 的弧是 G1、卡片的弧是 G2,两者之间会留一条最宽约 10px、没被模糊覆盖的月牙。对照图见 `.cache/corner-sheet.png`(①/⑪/⑫ 三列)。

**顺带更正**:"中间卡看不见圆角"当时判成"洗色对比不足",那只对了一半 —— 真底楔形是 254、卡内是 240,本来就有 14 级差;是这块漏出来的方角把边界糊成了一条没有转角的软带,所以补深 `--chat-veil`(→ 弧对比 mean 26.5)之后角仍显得"方"。两件事都要修,顺序无所谓。

## 4.3 毛玻璃与透明

- 窗口基底:`background: var(--window-bg); backdrop-filter: blur(28px) saturate(1.4)`(Electron 侧需 `transparent: true` 窗口配合,见 7.3);
- 右侧表情面板:独立一层 `blur(20px)`;
- **注意**:`backdrop-filter` 必须与"同层裁剪"配套,否则模糊会溢出圆角。G1 时代同层裁剪就是 `overflow:hidden`;4.1.1 用原生 `corner-shape`,它会让 `overflow` 的裁切轮廓一起变成超椭圆,所以 `.window` 的 `overflow:hidden` 原样保留、磨砂留在 `.window` 自身,`.bg-layer` 不承担裁剪。(被否决的 `clip-path` 路线不带 `overflow` 裁切,才需要把填充和磨砂下沉一层——见 4.1.1。)
- **红线**:不要在带磨砂的后代之上任何祖先加 `filter`——那会造 backdrop root,页内磨砂就采不到东西了。`corner-shape` 与 `clip-path` 都不是 `filter`,这条不被触碰。

### 4.8.1 入场曲线与退场曲线是两条(2026-10-11 本轮14 实测)

**退场不能复注入场的强减速曲线**。`--ease`(`cubic-bezier(.32,.72,0,1)`)用在最小化退场上时,85% 的行程被压进头 80ms——实测该腿在 79ms 就已经走完 scale 全程的 85.6%(0.6577 / 目标 0.6),100ms 走到 92.9%,后面全是肉眼分不出的尾巴,观感就是"帧率太低"。

新增两条令牌(`tokens.css`):

| 令牌 | 值 | 用途 |
|---|---|---|
| `--ease-exit` | `cubic-bezier(0.4, 0, 1, 1)`(强加速) | 退场类动效(目前只有最小化) |
| `--t-minimize` | `180ms` | 最小化退场时长 |

配套:退场期间给 `.window--minimizing` 挂 `will-change: transform, opacity`(只在退场期间挂,常驻会一直占一份层纹理)。三腿实测(同一次 `--minanim` 运行,`presented` = `capturePage` 160×160 小块的位图哈希去重帧数 / 调用次数,`raf` = 主线程帧距 p50/p95/max):

| 腿 | 注入 | `presented` | `raf` p50/p95/max |
|---|---|---|---|
| `off`(撤掉本轮两条优化) | `will-change:auto` + 用回 `--ease` | 13/16 | 7 / **13** / **20** |
| `on`(出厂态) | 无 | **17/19** | 7 / 9 / 12 |
| `bd`(再退掉退场期间的 backdrop blur) | `backdrop-filter:none` | 15/22 | 7 / 7 / 11 |

出厂态曲线读数是均匀铺开的:26ms 0.9955 → 66ms 0.9428 → 100ms 0.8694 → 142ms 0.7572 → 184ms 0.6229(scale,全程 `1 → 0.6`);而 `off` 腿 24ms 还是 1.000、**79ms 已到 0.6577**(走完全程 85.6%)、100ms 到 92.9% ⇒ 位移几乎全挤在头 80ms,后面全是肉眼分不出的尾巴。

`bd` 这条腿要如实报:它的 `raf`(7/7/11)甚至比 `on`(7/9/12)略好,`presented` 是 15/22 对 17/19(去重帧更少而调用更多)—— 三腿的 `calls` 本身就在 16/19/22 之间抖,说明**这个仪表在 backdrop-filter 这一档分不出胜负**。所以保留 `backdrop-filter` 的依据是"**收益未证 + 观感损失确定**",不是"实测无差异"。

**仪表的 run-to-run 离散**:同一条 `on` 腿两轮分别量到 15/18(p95 7 / max 11)与 17/19(p95 9 / max 12),`off` 腿是 11/16 与 13/16。`presented` 的绝对值会被 `capturePage` 自己的吞吐带走 ±2 帧,所以阈值要设在"**同一轮内各腿的相对次序 + 曲线形状**"上,不要拿单轮绝对值当门限;曲线形状两轮完全一致(`off` 永远在 80ms 内走完 85%),那才是稳的依据。

三条硬约束(都是实测换来的):

1. **组件源码保持与上游一致**,所有与令牌冲突的部分改在 `app.css` 的「reactbits 动效层适配」段;JS 侧颜色一律经 `src/lib/palette.ts` 读 CSS 变量,不许在组件 props 里写死 hex。两个件有相反的口径,别记混:GooeyNav 的 `color`/`activeTextColor`/`colors` 会被组件内 `parse()` 解析,**只认 `#hex` 与 `rgb()`**,必须传 palette.ts 取到的实际值,而 `--gn-ink` 那批主题变量写在 `<nav>` 的**内联 style** 上、CSS 类盖不住,只能用它的 `style` prop 覆盖;FoldText 的 `color`/`fontSize`/`fontWeight` 只是被写成 `--fold-text-*` 自定义属性,不经 JS 解析,所以传 `'var(--text-1)'` 安全,且因为它们落在内联样式上,想改也只能走 props。HoldButton 同这一类:四个颜色只进内联 `--hb-*`(液面与盒体共用 `clip-path: inset(0 round var(--hb-radius))`,所以它**刻意不进 G2 清单** —— corner-shape 不改 clip-path 的角形,只换盒体会让按住时的液面与角错开),尺寸则在适配段用 `.phrase-chips .hold-button` 压回 chip 档(几何由组件自己 offsetWidth/Height 实量,压小安全)。
2. **reduced-motion 统一兜底**:`src/lib/motionPref.ts` 读一次 `matchMedia('(prefers-reduced-motion: reduce)')`,每个接入点据此回退——背景退 `--flow` 静态渐变,AnimatedContent 退直接挂载。reactbits 组件大多不自带这个判断,**两个例外:GooeyNav**(mount 读 `matchMedia`,reduced 时直接 `settle()` 不放水珠、弹簧阻尼置 1)与 **FoldText**(JS 侧关掉 `rotateX/Y`、时长压到 ≤0.22s、折痕归零,CSS 里还有一条 `@media (prefers-reduced-motion: reduce){ transform:none!important }` 硬兜)——这两个宿主不再套一层。首版群名的 BlurText 不自带,所以当时外面包了 `reduceMotion ?` 三元,换件后已撤。
3. **不合适的坚决不接**:CountUp 因弹簧尾部渐近(发消息 2.6s 仍显示 9112/9178)被撤;AnimatedList/GlassSurface/GlareHover/光标类因越出「动效层」口径或偏离原型而未接。判据与数字记在许可文档,不靠印象。

- **拖拽(自绘,不用 `-webkit-app-region`)**:`.drag-region` 标记的带可起手,带内 `.no-drag` 元素不起手。`pointerdown` → `ipcRenderer.send('window:drag-start')`,之后每帧只发 `window:drag-move`(**不传坐标**),主进程用 `screen.getCursorScreenPoint()` 现读实时光标算 `目标 = 窗口原点 + (实时光标 − 起手光标)` ⇒ 不累计误差、丢帧下一帧补上。`pointerup` / `pointercancel` / 窗口 `blur` 都收尾(少 `blur` 会出现"切到别的程序回来再动一下鼠标,窗口被隐形搬走")。
  - **顶边贴住工作区顶 + 松手 = 最大化**(Aero 那套);松手时没动过(纯点击)不算。
  - **拖最大化的窗口**:起手只记 `wasMax`,等位移过起拖阈值(对齐 `SM_CXDRAG`,本机取 4 DIP,**不乘 DPR**)才 `unmaximize()` 并把光标落到标题带 `DRAG_GRAB_Y=24` 那条横线上、按新 bounds 重新锚定。**这条是被真 bug 逼出来的**:先前在 `drag-start` 里直接还原,导致"双击最大化之后再单击一下就恢复"。
  - 代价(已声明):放弃 OS 拖拽 ⇒ 放弃 Aero Snap 左右分屏吸附,只有顶边那条自己补了。
- **窗口控制条**:在**任意**拖拽带上右键 → 光标处浮出 120×44 的三钮条(最小化/最大化/关闭,走 `window.api.*`);点外部、Esc、窗口失焦即关;越界光标被 clamp 回窗口内 8px(常量 `WIN_MENU_W/H` 与 CSS 的 `padding/gap/按钮宽高` 是同一笔账的两半,改一处必须改另一处)。整棵树的 `contextmenu` 由页面接管,`webContents` 的 `context-menu` 事件实测触发 **0 次**。
- **最小化退场(自绘)**:点最小化先播 `.window--minimizing`(`translateY(28px) scale(0.6)`,`transform-origin: 50% 100%`,`--t-minimize 180ms` + `--ease-exit`,见 4.8.1),`transitionend` 收尾才真 `minimize()`,并有 400ms 兜底计时器(`prefers-reduced-motion` 下 CSS 是 `transition: none`,事件永远不来)。从任务栏点回来走主进程 `win.on('restore')` → 渲染层 `onRestore`,挂 `window--noanim` **摘类但不反向播**(restore 后头 ~160ms 渲染器不出帧,反向播等于给出一段近乎透明的窗口)。**已声明的未覆盖范围**:`Win+D` 与任务栏发起的最小化走 OS 路径,应用拦不到,那两种情况确实没有动画。
- **为什么非自绘不可**:OS 的"缩进任务栏"动画要求窗口带 `WS_SYSMENU`,Chromium 不给 `frame:false` 的窗口挂它。三臂实测:`frame:false` + 透明、`frame:false` + 不透明都**没有**动画,只有 `frame:true` **有**;注册表动画开关(`MinAnimate`/`EnableAnimations`)本机都是开的,所以不是系统关了动画。自绘的额外好处是它不读任何系统渲染路径,**Win10 与 Win11 跑的是同一条 `transition`**。
- 聊天主题切换即时生效,四元组令牌联动(见 3.6)。

## 7.3 主进程关键配置(透明圆角窗口 + 自绘窗口壳)

```js
// electron/main.ts(与代码逐项一致)
new BrowserWindow({
  title: APP_TITLE,
  width: 1280, height: 800,
  // 1248 = 2*10 窗口内边距 + 2*14 栏间隙 + 2*300 侧栏 + 600 中间区(= 2×300)
  minWidth: 1248, minHeight: 600,
  frame: false, transparent: true,          // 圆角由 CSS 裁剪
  backgroundColor: '#00000000',
  show: false,
  webPreferences: { preload: path.join(__dirname, 'preload.js'),
                    contextIsolation: true, nodeIntegration: false, sandbox: true },
});
win.on('restore', () => win.webContents.send('window:restored'));   // 退场留下的类靠这条摘(6.4)
```

IPC 面(全部在主进程):`window:minimize` / `window:maximize`(双向 `isMaximized → unmaximize`)/ `window:close` 走 `handle`;`window:drag-start` / `-move` / `-end` 走 `on`(**零参数**,位移由 `screen.getCursorScreenPoint()` 现读)。preload 用 `contextBridge.exposeInMainWorld('api', …)` 暴露 7 个方法(见 5.3 的 `WindowChrome` 契约)。

渲染层对应:`html,body{background:transparent}`;根容器 `border-radius: var(--r-window); overflow: hidden; backdrop-filter: blur(28px) saturate(1.4)`。**拖拽区不再有 `-webkit-app-region`**:`.drag-region` 只剩 `user-select:none` + 一个给 JS 读的类,`.no-drag` 是纯 JS 契约(CSS 侧不声明,类留在元素上就是给 `closest()` 读的)。

主进程侧的自绘拖拽与三项控制集中在 `window:drag-start/move/end` 与 `window:minimize/maximize/close` 六个 handler 上(位移用 `screen.getCursorScreenPoint()` 现读,`DRAG_SLOP = 4` DIP 起拖阈值、`DRAG_GRAB_Y = 24` 还原后光标落点),渲染层对应用 `<WindowChrome/>` 接(5.2、6.4)。

主进程入口尽早挂两条空 error 处理器:`process.stdout.on('error', () => {})`、`process.stderr.on('error', () => {})`。**成因是真实事故**:跑取证脚本时管道读端先退出(一条 `grep -oE` 的正则括号不配平),主进程的 `console.log` 抛 EPIPE,Electron 直接弹了一个模态错误框到用户脸上。附带纪律:探针输出一律重定向到文件,不接管道。

> 已知坑:Windows 上 `transparent` 窗口关不掉原生阴影则自行补 `--shadow-window`;DWM 圆角裁剪毛边用 1px 内边距 + `border` 同色收边。
